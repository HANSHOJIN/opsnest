## 1. “服务器总管”是什么

服务器总管不是普通聊天窗口，也不是直接把用户文本拼接成 Shell 命令。它是跨服务器的任务入口和 AI 编排层：

1. 先根据输入解析目标服务器；明确提到某台服务器时只锁定该服务器，提到“所有/每台/集群”时才展开到全部可用服务器。
2. 将服务器清单、服务器画像、历史记忆和当前请求交给 AI。
3. AI 返回结构化工具调用或计划；本地 AgentRuntime 决定是否执行工具。
4. 执行链按 AgentRun 展示：上下文、记忆、搜索、环境探索、只读诊断、计划、审批、执行、验证、记忆更新。
5. 高风险或有副作用的命令必须经过本地风险判断和用户批准；执行后还要验证并写入本地日志/服务器记忆。

总管还承担少量确定性管理动作，例如自然语言添加/删除服务器、连接全部服务器、生成反向 SSH 隧道脚本和把已发现服务加入快捷入口。这些动作不是让模型自由执行，而是由 `features/manager/requests.ts` 先解析，再调用已定义的本地流程。

V2 应保留的定义：总管是“多服务器任务编排器”，不是服务器详情页的替代品，也不是无审批的远程 Shell。

## 2. AISSH 是什么

V1 中 AISSH 不是另一种 SSH 协议，而是同一台服务器的 SSH 终端中的 AI 工作模式。

- Shell 模式：输入直接进入本地持久 Shell，保持工作目录、虚拟环境和命令上下文。
- AI 模式：用户用自然语言描述目标；本地先形成计划/风险说明，再通过 Agent 工具执行 SSH 命令，结果回到同一个终端会话。
- 交互式命令：当 AI 需要运行交互式工具时，前端把命令交接给持久 PTY，并用唯一结束标记收集结果；这保证 AI 任务和用户看到的终端是连续的。
- 断线恢复：可见 PTY 断开后尝试重连，同时先关闭失效的普通持久 Shell，避免下一条命令落到死连接。
- 工作目录连续性：通过同一持久 Shell 读取 `PWD` 和虚拟环境，命令完成后重新绘制提示符。

因此，V2 的 AISSH 目标是“无缝 SSH + AI”，而不是把 AI 回复另开一个聊天页面。必须避免重复挂载终端、重复创建 PTY、AI 会话与用户终端上下文分裂。

## 3. 服务器总览卡片

服务器总览卡片是资产列表页的摘要卡，不是完整服务器主页。它展示：

- 名称、`username@host:port`、连接状态和延迟；
- 系统图标与系统名称；
- 连接后读取的 CPU 核数、内存、磁盘、Docker 状态/运行容器数；
- 未扫描时明确显示“连接后读取资源”，不伪造指标；
- 双击进入服务器特色主页；按钮按状态执行“连接”或“打开 SSH”；
- 编辑入口只编辑服务器资产信息。

卡片的数据来源是 `Server` 加可选的 `ServerProfile`。它应保持快速、可扫读、低密度；详细服务入口、硬件扫描和设备特性放在特色主页。

## 4. 服务器特色主页

进入单台服务器后，V1 按画像选择不同主页，而不是所有服务器共用一张空白详情页：

- 普通 Linux：运行概览、系统资源、SSH、已安装/运行服务、Web 管理入口、Docker、定时任务和 AI 快捷操作。
- OpenWrt/路由器：WAN/LAN、内网客户端、Wi-Fi 客户端、固件/内核、内置服务、插件和 Docker；使用路由器专属布局。
- NAS/fnOS：存储与服务概览、Docker 容器、NAS 应用和管理端口；使用 NAS 专属布局。

共同的数据流程是：

1. SSH 连接成功后执行只读 `inspect_server`，得到 `ServerProfile`。
2. 用户手动触发或 AI 请求触发服务发现，后端用带 `OPSNEST_*` 标记的只读脚本解析服务、端口、版本、运行状态和 Web 路径。
3. 主页将 SSH、发现的服务和自定义服务统一呈现为可操作入口；服务入口只打开已解析的管理 URL，不把未知字符串直接当成 URL。
4. 扫描时间和服务入口写回服务器资产，供总览卡片和下一次 AI 上下文使用。

V2 应继承“按服务器类型呈现特色主页”的能力模型，但重新设计在 CodexShell/OpsNest 外壳中的布局，不复制 V1 的旧页面结构。

## 5. ICON 系统的定义

ICON 系统是一个“语义键 -> 候选图标 -> 本地/远程资源 -> 可用回退”的解析层，不只是静态图片目录。

### 系统图标

`getSystemIconKey` 根据 `osId`、`osName`、主机名和设备画像识别 Linux、Debian、Ubuntu、OpenWrt、fnOS/NAS 等语义类型，再生成带版本和别名的候选键。

### 服务图标

`ServiceIcon` 根据服务 ID/名称/类别/版本匹配 Docker、Nginx、1Panel、数据库、面板和常见服务；允许服务入口编辑端口和管理路径，并将修改回写到发现服务。

### 资源优先级

1. 内置打包 SVG/PNG，保证离线可用；
2. GitHub 图标目录的远程 SVG/PNG，带超时和内存缓存；
3. WebView localStorage 缓存，作为可选加速层；
4. 语义占位符作为最终回退。

候选键会做小写、连字符、版本号和别名归一化，例如服务版本优先匹配 `name@version`，再回退到 `name` 和别名。

V2 的 ICON 定义应改为：

- 语义 ID 与视觉资源分离；
- 本地资源优先，远程目录可选；
- 图标缺失不能影响服务器、服务或页面功能；
- 系统图标、服务图标、状态图标使用不同命名空间；
- 结合新 portable `data` 目录缓存，但不把远程图标作为运行必需依赖。

## 6. V1 能力到 V2 的迁移结论

必须保留的行为能力：

- 服务器资产、服务器画像和本地活动日志；
- 只读服务器扫描与服务发现；
- 普通 Linux/OpenWrt/NAS 的特色主页数据模型；
- 持久 SSH Shell、PTY、工作目录连续性、断线重连；
- AISSH 的自然语言计划、工具调用、审批、执行、验证；
- AgentRun 可观察过程；
- 系统/服务 ICON 的语义解析和离线回退。

必须重新实现的部分：

- 页面和卡片视觉结构；
- 外壳中的四栏/标签/面板挂载方式；
- V2 新数据格式和 portable `data` 存档；
- 旧版 localStorage、旧存档和旧 UI 不迁移。
